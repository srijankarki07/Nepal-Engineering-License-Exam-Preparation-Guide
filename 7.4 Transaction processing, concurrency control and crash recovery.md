## 7.4 — Transaction Processing, Concurrency Control, and Recovery

### 1. What is a Transaction?

A **transaction** is a logical unit of work that performs one or more database operations (like `INSERT`, `UPDATE`, `DELETE`) and must execute **completely or not at all**.

Example:
Transferring money between two accounts<br>

1. Withdraw from A<br>
2. Deposit to B<br>

Both must happen, or none.

---

### 2. ACID Properties

To ensure reliability, every transaction follows **ACID**:

| Property            | Meaning                                         | Example                                     |
| ------------------- | ----------------------------------------------- | ------------------------------------------- |
| **A — Atomicity**   | All or none                                     | Money deducted but not deposited → rollback |
| **C — Consistency** | DB must remain valid                            | Balance should not disappear                |
| **I — Isolation**   | No interference between concurrent transactions | Two people booking same seat                |
| **D — Durability**  | Once committed, permanent even after crash      | Power cut → still saved                     |

---

### 3. Transaction States

| State                   | Meaning                                |
| ----------------------- | -------------------------------------- |
| **Active**              | Executing operations                   |
| **Partially Committed** | All operations done, waiting to commit |
| **Committed**           | Changes saved permanently              |
| **Failed**              | Error occurred                         |
| **Aborted**             | Rolled back, no changes made           |

_Tip:_<br>
After abort → rollback → back to consistent state.

---

### 4. Schedules

A **schedule** defines how transactions are executed (order of read/write operations).

| Type                    | Description                                            |
| ----------------------- | ------------------------------------------------------ |
| **Serial Schedule**     | One transaction executes fully before another starts   |
| **Concurrent Schedule** | Operations interleaved (faster, but risk of conflicts) |

---

### 5. Concurrency Problems

When transactions execute concurrently, these issues may occur:

| Problem               | Description                                     | Example                             |
| --------------------- | ----------------------------------------------- | ----------------------------------- |
| **Dirty Read**        | T2 reads uncommitted changes of T1              | If T1 rolls back, T2 has wrong data |
| **Unrepeatable Read** | Same query returns different results            | T2 updates between T1’s two reads   |
| **Lost Update**       | Two transactions overwrite each other’s updates | Both editing same record            |
| **Phantom Read**      | New rows appear/disappear during re-execution   | T2 inserts during T1’s read         |

_Tip:_<br>
**Dirty, Lost, Unrepeatable, Phantom = concurrency villains!**

---

### 6. Concurrency Control Techniques

Used to ensure correct concurrent execution.

#### **A. Lock-Based Protocols**

- Transactions **lock data items** before using them.
- **Types:**

  - **Shared Lock (S):** For read (multiple allowed)
  - **Exclusive Lock (X):** For write (only one allowed)

#### **Two-Phase Locking (2PL) Protocol**

1. **Growing Phase** – Acquire locks<br>
2. **Shrinking Phase** – Release locks<br>
   Ensures **serializability** (safe ordering)

_Rule:_
Once a lock is released, no new lock can be obtained.

---

#### **B. Timestamp Ordering**

- Each transaction gets a timestamp.
- Execution order based on timestamp.
- Prevents conflicts without locks.

---

#### **C. Deadlock**

Occurs when two transactions wait for each other’s locked resources.

_Example:_<br>
T1 locks A, waits for B.<br>
T2 locks B, waits for A → **Deadlock!**

**Prevention Methods:**

- **Timeouts**
- **Wait-Die / Wound-Wait schemes**
- **Deadlock Detection (using Wait-for Graph)**

---

### 7. Recovery System

To restore database after crash/failure.

#### **Failure Types:**

| Type                    | Example                          |
| ----------------------- | -------------------------------- |
| **Transaction Failure** | Logical error (divide by zero)   |
| **System Crash**        | Power or OS failure              |
| **Disk Failure**        | Data corruption, hardware damage |

---

### 8. Log-Based Recovery

DBMS keeps a **log** (sequential record of all actions).

Each log entry:
`<Transaction_ID, Data_Item, Old_Value, New_Value>`

**On failure:**

- **Undo:** Roll back uncommitted transactions
- **Redo:** Reapply committed ones

_Rule:_<br>
**UNDO before REDO**

---

### 9. Checkpoints

Periodic snapshots of database state → reduces recovery time.

**When crash occurs:**<br>
→ Start recovery from last checkpoint, not from the beginning.

Think: **Save game progress**

---

### 10. Shadow Paging (Alternative to Logging)

- Maintains **two copies** of database pages:

  - **Current Page Table (active)**
  - **Shadow Page Table (stable)**
    → If crash happens, revert to shadow.

**1. ACID property ensuring transaction executes completely or not at all:**<br>
A. Consistency<br>
B. Atomicity<br>
C. Isolation<br>

**Answer:** B

**2Which phase in 2PL allows acquiring locks?**<br>
A. Growing<br>
B. Shrinking<br>
C. Waiting<br>
D. Unlocking

**Answer:** A

---

**3. Dirty Read occurs when:**<br>
A. A transaction reads uncommitted data from another<br>
B. A transaction writes before commit<br>
C. A transaction aborts<br>
D. Two transactions update same row

**Answer:** A

---

**4. Deadlock can be prevented by:**<br>
A. Two-phase locking<br>
B. Wait-for graph<br>
C. Timestamp ordering<br>

**Answer:** D

**5. A transaction that completes all operations successfully but not yet committed is in:**<br>
A. Active<br>
B. Partially Committed<br>
C. Failed<br>
D. Aborted

**Answer:** B

---

**6. In recovery, redo operation is applied to:**<br>
A. Uncommitted transactions<br>
B. Committed transactions<br>
C. Aborted transactions<br>
D. Failed transactions

**Answer:** B

---

**7. Checkpoint in DBMS helps in:**<br>
A. Increasing transaction speed<br>
B. Reducing recovery time<br>

**Answer:** B

**8. Shared lock allows:**<br>
A. Only read operations<br>
B. Only write operations<br>
C. Both read and write<br>

**Answer:** A

**9.If T1 waits for T2 and T2 waits for T1, it is:**<br>

**10. The correct order during crash recovery is:**
