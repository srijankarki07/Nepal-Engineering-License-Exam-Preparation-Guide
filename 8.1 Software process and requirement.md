# **8.1 Software Process and Requirements**

## **1. Software Characteristics**

These describe how software is **different from hardware**.

### Key Characteristics

1. **Software is developed, not manufactured**

   - No factory production
   - Cost is mostly in development, not duplication

2. **Software does not wear out**

   - Hardware fails due to wear and tear
   - Software fails due to **bugs or changes**

3. **Software is mostly custom-built**

   - Though reusable components exist

4. **Software is intangible**

   - You can’t touch it

---

## **2. Software Quality Attributes**

These define **how good** a software system is.

### Common Quality Attributes (memorize)

| Attribute           | Meaning                      |
| ------------------- | ---------------------------- |
| **Correctness**     | Does it meet requirements?   |
| **Reliability**     | Works without failure        |
| **Efficiency**      | Uses minimal resources       |
| **Usability**       | Easy to use                  |
| **Maintainability** | Easy to modify               |
| **Portability**     | Works on different platforms |
| **Security**        | Protects data                |
| **Scalability**     | Handles growth               |

---

## **3. Software Process Model**

A **process model** defines **how software is developed**.

---

### **a) Agile Model**

- Iterative and incremental
- Customer involvement is continuous
- Fast feedback
- Embraces change

Best for:

- Changing requirements
- Small to medium projects

Not good for:

- Very large, safety-critical systems

  **Keywords:**
  `Iterative`, `Customer collaboration`, `Flexible`

---

### **b) V-Model**

- Extension of Waterfall
- Each development phase has a **testing phase**

| Development   | Testing             |
| ------------- | ------------------- |
| Requirements  | Acceptance testing  |
| System design | System testing      |
| Architecture  | Integration testing |
| Coding        | Unit testing        |

- V-Model emphasizes **verification & validation**

---

### **c) Iterative Model**

- Develop in **repeated cycles**
- Each iteration improves the system

Key idea:

> “Build → Evaluate → Improve”

---

### **d) Prototype Model**

- First build a **quick prototype**
- Helps understand requirements clearly

Used when:

- Requirements are unclear

Risk:

- Poor design if prototype is rushed into final product

  Used for **requirement clarification**

---

### **e) Big Bang Model**

- No planning
- Code everything at once

  Highly risky<br>
  Not suitable for large projects

Best suited for **small experimental projects**

---

## **4. Computer-Aided Software Engineering (CASE)**

CASE = **Tools that support software development**

### Examples:

- Requirement tools
- Design tools (UML tools)
- Testing tools

### Types:

- **Upper CASE** → Requirements & design
- **Lower CASE** → Coding & testing
- **Integrated CASE** → Full lifecycle

  CASE tools improve **productivity and quality**

---

## **5. Functional & Non-Functional Requirements**

### Functional Requirements

- **What the system does**
- Features & functions

Example:

> User can login, register, place order

---

### Non-Functional Requirements

- **How the system performs**
- Constraints & qualities

Example:

- Performance
- Security
- Reliability

- _Speed, security, usability_ → **Non-functional**

---

## **6. User Requirements vs System Requirements**

| User Requirements | System Requirements |
| ----------------- | ------------------- |
| High-level        | Detailed            |
| Natural language  | Technical           |
| For users         | For developers      |

User requirements are **less technical**

---

## **7. Interface Specification**

Defines **how systems or components interact**

Includes:

- Input/output formats
- APIs
- Communication protocols

---

## **8. Software Requirements Document (SRS)**

SRS = **Formal description of system requirements**

### Contains:

- Functional requirements
- Non-functional requirements
- Constraints
- Interface details

  SRS is used as a **contract** between client and developer

---

## **9. Requirement Elicitation & Analysis**

### Requirement Elicitation

How requirements are **collected**

Techniques:

- Interview
- Questionnaire
- Observation
- Workshops

---

### Requirement Analysis

- Resolve conflicts
- Remove ambiguity
- Prioritize requirements

  Identifying conflicting requirements → **Analysis**

---

## **10. Requirement Validation**

Ensures requirements are:

- Correct
- Complete
- Feasible
- Testable

Methods:

- Reviews
- Prototyping

---

## **11. Requirement Management**

Deals with **changes in requirements**

Includes:

- Version control
- Change tracking
- Impact analysis

  Managing requirement changes → **Requirement management**

---

## **Quick Summary**

- Software doesn’t wear out
- Agile = flexible
- V-Model = testing aligned
- Prototype = unclear requirements
- Functional = what system does
- Non-functional = quality attributes
- SRS = formal requirement document
- CASE tools support development
- Requirement management handles changes
